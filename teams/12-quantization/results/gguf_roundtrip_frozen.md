# GGUF round trip: tokenizer frozen

Generated by `tokenizer/gguf_roundtrip.py` on 2026-11-13 (arm64 Darwin, CPU). Do not edit by hand; rerun the script.

**Question.** Does llama.cpp, after GGUF conversion, cut text into the **same token ids** as the Hugging Face tokenizer the model is trained with? Gate 2 bar (TSAI, 2 Nov): same ids on every line; same decoded text alone is not enough.

**Pass per line:** (1) GGUF ids == HF `tokenizers` ids; (2) GGUF detokenize(ids) == the original bytes. Special-token strings are parsed on both sides, as HF does by default. Checked with llama-cpp-python, line by line. The `llama-tokenize` column repeats the check with the llama.cpp build's own binary, on each set joined into one text with newlines.

**Normalizer.** This tokenizer.json has a normalizer (Sequence, 16 steps). The GGUF format has none, so llama.cpp tokenizes the text as it is while HF normalizes it first. The **raw** pass compares them as they are; the **normalized** pass applies the normalizer first and compares llama.cpp on that text with HF on the same text (HF without its normalizer), so the dropped normalizer is the only difference left. Normalize-then-tokenize is also checked against HF's own pipeline on every line.

The stock converter (no `--pre` override) says: `NotImplementedError: BPE pre-tokenizer was not recognized - update get_vocab_base_pre()`

**What it means.** **No tested llama.cpp pre-tokenizer gives the same ids on every line and every vocabulary token: blocker for G3 and G12.** The closest is `granite-embed-multi-97m`: apart from the lines the normalizer changes, 1 test line(s) and 9 vocabulary token(s) differ.
`gpt-4o` decodes every line back to the same text, but cuts 12,309 lines into different tokens. A check of decoded text alone would pass it; the model would see ids it was not trained on.

**Normalizer.** llama.cpp alone does not reproduce the training ids on the 3,074 lines whose text the normalizer changes (3,074 of 20,400 lines are changed). With the normalizer applied first those lines match (see the normalized pass). A serving app that uses llama.cpp must run the normalizer on the text before tokenizing; the GGUF cannot carry it.

**Pre-tokenizer.** What differs besides the normalizer: 1 test line(s) (by set: rus_Cyrl 1) and 9 vocabulary token(s) (9 of the tokens are all-capital words with an accented capital that end in an ASCII capital). The pattern llama.cpp uses for this type (`src/llama-vocab.cpp`) tells upper from lower case with the ASCII ranges `[^a-z]` and `[^A-Z]`, while tokenizer.json's regex uses `\p{Lu}` and `\p{Ll}`. For cased letters outside ASCII (accented Latin, Cyrillic, Greek) the two cut words differently where the case changes, for example a word in CamelCase or an all-capital word with an accented capital. Running both regexes with the `regex` package gives a different cut for 1 of 1 lines and 9 of 9 tokens. Scripts without case (every Indic script and the code sets here) are not affected: none of their test lines differs for this reason. Text with such words (all-capital headings, CamelCase in Cyrillic or Greek) gets different ids from llama.cpp; the line numbers and token ids are in the .json.
